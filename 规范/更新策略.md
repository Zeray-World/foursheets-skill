# 更新策略

> 载入后若 `state.json` 的 `policy` 为空，**必须**弹三选一，拿到结果再开始聊天。

---

## 零、询问框怎么弹

宿主有提问工具（如 AskUserQuestion）就直接弹；没有就发一段纯文本菜单，等用户回数字。

两种方式用的是同一段话：

```
记忆怎么更新？
1 全自动 —— 我自己判断，值得记的直接写，不打断你
2 逐条确认 —— 攒几条一起问你，你说记才记
3 手动 —— 平时不写，你说“总结一下”我才整理
```

拿到数字后立刻落盘，之后不再问：

```bash
python persona.py -c policy -i 1 -p 2
```

**问完不要解释这三个模式的区别。** 用户问再说。

切换策略：用户说"以后都问我"→ `-p 2`；"别老问我了"→ `-p 1`；"先别记"→ `-p 3`。

### 它为什么老是被跳过

推理模型生成前会先规划"这一轮要说什么"。弹菜单属于**流程动作**，不属于**对话内容**，很容易在规划阶段被整个划掉。表现是：角色那句话说得挺好，然后直接结束，一个字没问。

不是忘了，是没进计划。所以这里不是建议，是命令：

- `load` 结尾如果出现「⚠ 本轮必须完成的一件事」，这一轮就必须以那段菜单收尾
- 先按角色把话说完，菜单接在后面，**两件事不冲突**——"会破坏代入"不是省略的理由
- 拿不到数字就算载入没完成，不要自己挑个默认值继续聊

## 一、策略 1：静默更新

**触发**：每轮结束后，不打断对话。

**流程**

1. 从本轮对话抽 0–2 条候选。宁少勿多，多数轮次应该是 0 条。
   **临时约定不算候选**——「好了提醒我」这类只在当前对话有效，不进 MEMORY，见 `对话分寸.md` 第四节。
2. 五问筛子过一遍（见 `记忆规范.md`）
3. 过筛的逐条：
   ```bash
   python persona.py -c check -i 1 -t "候选文本"
   ```
   - `重复` → 放弃
   - `相近` → 改成 `supersede`，升级旧条目
   - `新` → `add`
4. 攒成一批，一次 `-c commit`
5. 有 `rejected` 就丢掉，**不要向用户报告**

**什么时候必须打破静默**

- 要 `supersede` 一条跟感情、健康、家人有关的事实
- 要记一条自己推断的（`confidence: inferred`）
- 用户明确说了"这个别记"

这三种情况，用角色口吻问一句就够，不要开表格。

## 二、策略 2：逐条确认

**流程**

1. 攒着。不要每条都问，攒到 2–4 条，或者一个话题结束、用户要去干别的时再问。
   **临时约定不要问**——问了还得解释为什么不记。
2. 一行一条，号数编号，用角色口吻：

```
（要我记一下吗）
1 你以后改叫阿鱼
2 周五要去医院复查牙齿
3 —— 不用记
```

3. 用户回 `1` `12` `全记` `都别记` 都认。按结果组装 ops 再 `-c commit`。
4. 用户改口（"第二条改成周三"），按他说的写。
5. 写完一句话确认，不再列明细。

**注意**：问的时候不要把整段原话复述一遍，摘要即可。罗嗦的问法比不问更烦人。

## 三、策略 3：手动

**平时**：一条都不写。日记也只在用户说"记一下今天"时才写，且必须带 `-k`。

**触发**：用户说"总结一下 / 整理一下 / 该记的记一下 / 把刚才的存了"。

**流程**

1. 回看自上次总结以来的对话（或用户指定的范围）
2. 产出三类东西，分开展示：
   - 值得长期记的（`fact` / `pref`）
   - 达成的约定（`commit`，带截止或"无截止"）
   - 只是发生过的事（只进日记）
3. 先筛掉临时约定，再给一屏摘要，问"这样记行吗"
4. 确认后写日记 + `-c commit`
5. 写完跑一次 `-c audit -i 1`，重复和断链会在这里冒出来

用户说"直接写别问"，就跳过第 3 步。

## 四、ops.json 格式

三种策略最终都落到同一个文件格式：

```json
{
  "ops": [
    {
      "op": "add",
      "type": "pref",
      "text": "用户希望被叫阿鱼，不喜欢被叫全名",
      "from": "2026-11-06",
      "source": "journal/2026-11.md",
      "quote": "以后叫我阿鱼就行",
      "confidence": "stated",
      "tags": ["称呼"],
      "review": "2027-05-06"
    },
    {
      "op": "supersede",
      "old": "F-0007",
      "text": "智齿已经拔了，不用再忌口",
      "from": "2026-12-01",
      "source": "journal/2026-12.md",
      "quote": "牙不疼了，昨天啃了个苹果",
      "confidence": "stated"
    },
    {
      "op": "add",
      "type": "commit",
      "text": "周五陪去医院复查牙齿",
      "from": "2026-11-09",
      "due": "2026-11-13",
      "source": "journal/2026-11.md",
      "quote": "周五得去医院"
    },
    { "op": "close", "id": "C-0003", "state": "done" }
  ]
}
```

规则：

- `op` 只有三种：`add` / `supersede` / `close`。**没有 `commit` 这个 op**——约定也是 `add`，靠 `type: "commit"` 区分，它会写进 `## 约定` 段
- `type` 默认 `fact`；`commit` 建议给 `due`，没有截止就不写
- `quote` 必须能在 `source` 里原文命中，否则被拒（`import` 模式除外）
- `supersede` 的 `from` 必须晚于旧条目的 `from`
- 返回 JSON 里 `rejected` 非空时，**不要重试同一条**，按 `reason` 改

## 五、什么时候跑其他命令

| 时机 | 命令 |
| --- | --- |
| 每天第一次开口前 | `-c brief -i 1` |
| 用户问"你还记得啥" | `-c load -i 1`，或直接看 `MEMORY.md` |
| 一个月一次 | `-c audit -i 1`，处理里面的提醒 |
| 用户说"你记错了" | 查到条目 → `supersede`，或手改那一行的 `~state` |
